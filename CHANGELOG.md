# Changelog

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).

## [Unreleased]

### Исправлено

- **`request.post` на chromedp-бэкенде отправлял двойное URL-кодирование.** Приватная копия
  `buildPostFormHTML` в `server/browser/chromedp` применяла `url.QueryEscape` поверх
  `html.EscapeString`, из-за чего значение `P@ss` приходило на сервер как `P%2540ss` — молча ломая
  любую форму со спецсимволами. chromedp — это резервный бэкенд, на который проект переходит сам при
  отсутствии `chromedriver`, то есть на типовой инсталляции. Исправление в `common.go` было сделано
  давно, но до копии не дошло.
- **Браузеры и временные каталоги утекали при каждом `SIGTERM`.** `main` завершался раньше, чем
  отрабатывал `Shutdown`, поэтому `service.Close()` (единственный вызов `destroyAll`) обычно не
  выполнялся. Дополнительно `Shutdown` прерывал цепочку очистки на первой ошибке, а запрос в полёте
  на момент остановки гарантировал такую ошибку.
- **`log_level` из `init.yaml` игнорировался.** `SaveConfig` его писал, но `applyConfigFile` не
  читал — уровень логирования, выставленный через `/settings`, терялся при следующем старте.
- **Все операции с сессиями сериализовались на время запуска браузера.** `sessionStore.create`
  держал глобальный write-lock во время `factory.New`, включая скачивание драйвера по сети.
- **Обращение к закрытой сессии.** Между выдачей сессии и захватом её мьютекса `destroy` /
  `destroyAll` успевали закрыть браузер; запрос уходил в «труп» и возвращал транспортную ошибку
  вместо `The session doesn't exist.`
- **Экспортёр Prometheus мог отключиться навсегда.** При ошибке остановки старого сервера
  `m.server` оставался указывать на так и не запущенный экземпляр, и все последующие `ApplyConfig`
  пропускали создание нового.
- **Гонка при сохранении настроек.** Два параллельных POST могли потерять обновление, а запись шла
  в фиксированный `init.yaml.tmp` — переплетение двух записей могло опубликовать полуфайл.
- **Двойной `Wait()` на процессе Xvfb.** Горутина внутри `StartXvfb` и `Process.Wait()` из
  `stopDisplay` состязались за один `wait4`; процесс мог остаться зомби.
- **`sessions.list` не отдавал ключ `sessions` при пустом списке**, хотя Python всегда возвращает
  `[]`.
- **`disableMedia: true` «залипал» на всю сессию** — список блокируемых URL выставлялся, но никогда
  не сбрасывался.
- Утечка файлового дескриптора лога geckodriver при `LOG_LEVEL=debug`.
- `Close()` в chromedriver-бэкенде мог блокировать остановку на 30 секунд на каждую зависшую
  сессию; теперь дедлайн 5 секунд и мягкая эскалация `Wait → SIGTERM → SIGKILL`, которая не оставляет
  осиротевший Chrome.
- Ошибка `Emulation.setUserAgentOverride` больше не проглатывается молча — от этого вызова зависит
  решение managed-челленджей.
- `geckodriver` при заданных логине/пароле прокси теперь пишет предупреждение вместо тихой потери
  учётных данных.
- Повторный идентичный GET в `fetchChromeForTestingText`, который не мог сработать.
- `geckodriver` на Windows распаковывался внутрь кэша `chromedriver`.
- Ошибка запуска Chrome при определении версии больше не теряется.

### Безопасность

- **CSRF на `/api/settings`.** Обработчик принимал любой `Content-Type` и не проверял `Origin`,
  поэтому кросс-доменный POST (*simple request*, без preflight) мог подменить `browser_path` /
  `driver_path` и добиться выполнения произвольного бинарника — с сохранением в `init.yaml`.
  Теперь требуется `Content-Type: application/json`, а кросс-сайтовые `Origin` / `Sec-Fetch-Site`
  отклоняются. Аутентификация по-прежнему не добавляется — это осознанное решение (см.
  [SECURITY.md](SECURITY.md)).
- `chrome_for_testing_url` принимается только по `https`; размер скачиваемого архива драйвера
  ограничен.
- `/v1` принимает только `http`/`https`: `file:///etc/passwd` и `chrome://` больше не открываются
  реальным браузером с возвратом HTML.
- HTTP-сервер получил `ReadHeaderTimeout` / `ReadTimeout` / `IdleTimeout` / `MaxHeaderBytes`;
  тела запросов ограничены по размеру. `WriteTimeout` намеренно не задан — solve легально идёт до
  `maxTimeout`.
- Валидация диапазона портов и запрет совпадения основного порта с прометеевским.

### Исправлено (интерактивный Turnstile на geckodriver)

- **Бэкенд geckodriver не мог решить ни один интерактивный челлендж** («подтвердите, что вы человек»).
  Причин было две, и обе устранены:
  - `solveChallenge` только ждал и двигал мышью, а `clickTurnstileCheckbox` вызывался лишь из
    `ApplyTurnstileToken` — то есть **после** успешного solve. Интерактивный челлендж сам не
    исчезает, поэтому цикл всегда вырабатывал все попытки и падал по таймауту. Клик перенесён внутрь
    цикла.
  - Сам поиск виджета шёл через `document.querySelector` в странице и всегда возвращал
    `no-widget, iframe_total=0`. Cloudflare рендерит Turnstile в **закрытом** shadow root: для
    страничного JS `el.shadowRoot === null`, а iframe внутри shadow-дерева не попадает даже в
    `window.frames` (спека исключает его из document-tree child browsing contexts). У Firefox нет
    аналога chromium-флага `--enable-blink-features=FakeShadowRoot`, которым пользуются два других
    бэкенда.

  Решение: не искать виджет силами страницы. Marionette отдаёт закрытые shadow root через сам
  протокол (`GET /session/:id/element/:id/shadow`), поэтому путь до чекбокса проходится ссылками на
  элементы: обход shadow-деревьев → `SwitchToFrame` в iframe `challenges.cloudflare.com` → второй
  обход внутри него → нативный `POST /element/:id/click`. Успех подтверждается через
  `GET /element/:id/selected`, а не фактом отправки клика.


- В `w3c` добавлены element-примитивы (`FindElements`, `FindElementsInShadow`, `ShadowRoot`,
  `ClickElement`, `ElementSelected`, `SwitchToFrame`, `SwitchToDefaultContent`) и типизированная
  `DriverError` с кодом ошибки W3C. Последнее было обязательным: Firefox отвечает на
  `no such shadow root` с **пустым** `message`, и прежний код терял такой ответ в безымянной
  `http 404`, из-за чего обход не мог отличить «здесь нет shadow root» от сбоя драйвера.

### Исправлено (снимок страницы и прокси)

- **Пайплайн мог снять недопарсенный документ.** Челлендж перестаёт детектироваться в момент, когда
  переход на настоящую страницу только **начинается**, а HTML читался сразу после этого. На живом
  интерактивном челлендже это давало 1439 байт с обрывом на `</head>` и без `<body>` при
  `waitInSeconds=0` — против полных 12 КБ при `waitInSeconds=2`. Теперь в `browser.Page` есть шаг
  `DocumentReady`, а `ResolvePage` опрашивает его до снимка (бюджет 10 с, шаг 200 мс) вместо того,
  чтобы вынуждать вызывающего угадывать паузу. Цикл живёт в пайплайне, бэкенд отвечает только на
  сам вопрос. Гонка была общей для всех трёх бэкендов; заметной она стала на geckodriver, потому что
  до сих пор он до этой точки на интерактивных челленджах просто не доходил.

- **Неразбираемый прокси означал запрос с реального IP.** geckodriver писал `ignoring proxy` и шёл
  напрямую, а chromedriver и chromedp отдавали неразобранную строку в `--proxy-server`, который
  Chrome молча отбрасывает — с тем же результатом. То есть опечатка в `proxy.url` приводила ровно к
  тому, чего прокси и должен был не допустить, и сообщала об этом строчкой лога. Теперь
  `browser.ValidateProxy` проверяется один раз в фабрике, до выбора бэкенда, и непригодный прокси
  делает создание браузера ошибкой: `unusable proxy: … (refusing to fall back to a direct
  connection)`.

- Заодно устранено расхождение между движками: `browser.ParseProxyURL` принимает `host:port` без
  схемы (так делает `--proxy-server` и так пишут в конфигах). geckodriver такую запись отвергал и
  уходил напрямую, то есть одна и та же настройка работала на одном бэкенде и молча не работала на
  другом.

- **Прокси с логином/паролем на chromedriver отправлял запрос мимо прокси.** Учётные данные этот
  бэкенд подставлял через MV3-расширение, которое загружалось ключом `--load-extension`, — а Chrome
  этот ключ убрал (обходной `--disable-features=DisableLoadExtensionCommandLineSwitch` тоже больше не
  действует). Замерено на Chrome 151 на локальном прокси: `--proxy-server` — 17 обращений,
  `--load-extension` — **0**. При этом `--proxy-server` стоял в ветке `else` этого расширения, то
  есть при заданных учётных данных не передавалось вообще никакого прокси-флага: запрос успешно
  уходил с реального IP, и в ответе не было ничего, что бы на это указывало.

  Расширение удалено целиком, `--proxy-server` передаётся всегда, а учётные данные теперь
  подставляются по CDP — тем же механизмом (`Fetch.authRequired`), которым всегда пользовался
  бэкенд `chromedp`. Обработчик вынесен в новый пакет `server/browser/cdpauth` и общий для обоих
  Chromium-бэкендов; chromedriver отличается только тем, что подключается к чужому браузеру по
  `goog:chromeOptions.debuggerAddress` из ответа на создание сессии.

  Проверено на локальном прокси с обязательной Basic-авторизацией: верный пароль — прокси пишет
  `AUTHED CONNECT`, ответ 200 и настоящая страница; неверный — `ERR_TOO_MANY_RETRIES` и никакого
  контента; Cloudflare на rutracker через авторизованный прокси решается штатно.

  Подводный камень зафиксирован в комментарии: `chromedp` принудительно сбрасывает признак «первого
  контекста» для `RemoteAllocator`, поэтому обычный `NewContext` **создаёт новую вкладку**, и
  перехват попадает на пустую страницу, которую никто не открывает. Нужен явный
  `WithTargetID` на ту вкладку, которой управляет chromedriver.

- **geckodriver научился авторизации на прокси** — раньше бэкенд просто предупреждал, что не умеет
  её, и запрос уходил на прокси без учётных данных. Причина была протокольная, а не в версии
  драйвера: Firefox открывает на 407 настоящее окно запроса логина
  (`nsIPrompt_promptUsernameAndPassword`), а классический WebDriver на `GET /alert/text` отвечает
  `no such alert` — отвечать нечем, навигация падает по таймауту. Проверено на самом свежем
  geckodriver v0.37.1 с Firefox 153, обновление здесь не помогает.

  Решение — WebDriver BiDi, который geckodriver отдаёт через капабилити `webSocketUrl`. Новый пакет
  `server/browser/bidi` — минимальный BiDi-клиент поверх WebSocket (подключение, JSON-RPC, подписка
  на события) плюс `InstallProxyAuth`: `network.addIntercept` на фазу `authRequired`, подписка на
  `network.authRequired`, ответ через `network.continueWithAuth`. Новых модулей не появилось —
  `gobwas/ws` уже был в графе зависимостей через chromedp.

  BiDi запрашивается только когда у прокси заданы учётные данные; в остальных случаях путь не
  меняется. Проверено на camoufox (Firefox 135) и на системном Firefox 153: прокси пишет
  `AUTHED CONNECT`, Cloudflare на rutracker через авторизованный прокси решается штатно.

  Две ловушки зафиксированы в коде:
  - Без `network.addIntercept` событие приходит, но запрос **не удерживается**, и
    `continueWithAuth` отвечает `no such request`.
  - Неверный пароль без ограничения попыток уходит в бесконечный цикл: замерено **613 запросов
    авторизации за 45 секунд**, после чего сессия не удалялась, geckodriver убивали по таймауту, а
    Firefox оставался сиротой. Теперь на запрос даётся одна попытка, дальше `action: "cancel"`:
    2 попытки, 7 секунд, чистое завершение.

- `geckodriver` запускается с индивидуальным `--websocket-port`. По умолчанию он фиксирован (9222),
  то есть два одновременных браузера дрались бы за один порт.

### Исправлено (рефакторинг бэкендов)

- **chromedp-бэкенд оставлял каталог профиля после каждого запроса.** `Close()` вызывал
  `allocCancel()` и сразу `RemoveAll`, но отмена контекста только сигнализирует Chrome о завершении
  и не ждёт его — ещё живой браузер заново создавал файлы профиля уже после удаления. Теперь
  используется `chromedp.Cancel`, который дожидается выхода процесса. Баг не был связан с
  рефакторингом и существовал раньше; найден при живой проверке (три эфемерных запроса оставляли три
  каталога).
- **Создание браузера больше не выпадает из бюджета `maxTimeout`.** `browserFactory.New` и все три
  конструктора принимают `context.Context`; он ограничивает readiness-опрос драйвера, создание
  сессии, установку stealth-скриптов и запуск Xvfb. Хуже всего был скан дисплеев Xvfb: до 100
  попыток по 5 секунд, то есть ~8 минут блокировки без какого-либо дедлайна. Автозагрузка драйвера
  намеренно осталась неограниченной, чтобы холодный старт не убивался малым `maxTimeout`.
- **Пропущенный кламп backoff в geckodriver.** Копия цикла ожидания готовности драйвера удваивала
  паузу без ограничения (50→100→200→400→800 мс); в webdriver кламп был. Теперь цикл один.
- **chromedriver осиротевал Chrome при остановке.** Он убивался сразу, тогда как geckodriver
  корректно эскалировал `Wait → SIGTERM → SIGKILL`. Теперь оба используют общую реализацию с
  эскалацией.

### Внутреннее

- Из `server/browser/chromedp` удалены приватные копии 19 хелперов, селекторов и структур — теперь
  все три бэкенда используют общие реализации из `server/browser/common.go`. Именно эта копипаста и
  породила баг с двойным кодированием.
- Разделяемый page-side JavaScript вынесен в `server/browser/scripts.go`; два побайтово одинаковых
  DOM-обходчика больше не живут в разных файлах.
- Собственный base64 заменён на `encoding/base64`.
- **Новый пакет `server/browser/w3c`** — единственная реализация W3C WebDriver поверх HTTP
  (`Session`) и управления процессом драйвера (`DriverProcess`). Раньше webdriver и geckodriver
  несли побайтово одинаковые копии `webDriverRequest`, `executeScript`, `currentCookies`,
  `setCookies`, `screenshot`, `pageTitle`/`currentURL`/`pageHTML`, `deleteSession`, `freeLocalPort`
  и цикла ожидания готовности — различались только тип receiver'а, префикс в тексте ошибки и пара
  имён локальных переменных.
- **Новый `browser.ResolvePage`** — единый пайплайн челленджа для всех трёх бэкендов через
  интерфейс `browser.Page`. Раньше это были три почти идентичные копии тела `resolve()`; именно
  поэтому geckodriver молча игнорировал `req.LogHTML` и per-request `disableMedia` — ничто не
  заставляло его их реализовать. Теперь добавление шага в `Page` обязывает каждый бэкенд ответить
  за него: geckodriver честно поддержал `LogHTML` и явно предупреждает про `disableMedia` вместо
  тихого игнорирования.
- Тесты на новый общий код: `w3c` против `httptest`-драйвера (конверт `{"value":…}`, сообщения
  ошибок, payload cookies, обёртка скриптов) и `ResolvePage` против фейковой `Page` — в том числе
  проверки **порядка** шагов, которые раньше держались только на комментариях.
- Суммарно по `server/browser/`: webdriver 1985→1502, geckodriver 1132→812, chromedp 1681→1150.
